# v80.8 — Cart role gate (addendum, 2026-10-28)

## The bug
Reported live by Gabriel (signed in as **admin**): he tapped **Add to cart** on the
menu for a service (a starter estimate) and the item silently filled his own
persistent **customer shopper cart** (`localStorage 'ghsCart'`) with a customer
toast. No client proposal, no order, nothing to send — while the actual tool for
that job, the admin cart builder, sat unused.

Root cause: `cartAdd(id)` and `orderNow(id)` in `app/public/index.html` had **no
role check**. `paintCartBtn()` already hid the floating cart button for
non-customer sessions, but the menu/wizard Add and Order buttons reached
`cartAdd` unchecked, and the shopper cart persists per-browser regardless of
who is signed in.

## The fix — two clean doors by role (owner's law, 2026-10-28)
A single helper, `cartRoleGate(id)`, now sits at the top of `cartAdd(id)` and is
checked first by `orderNow(id)`:

- **Guest / customer** — gate returns `false`; the flow is byte-for-byte what it
  was (shopper cart add, toast, `orderNow` → `#cart`).
- **Admin** (`me.role === 'admin'`) — the shopper cart is **never touched**. The
  service is routed into the cart builder via the existing `builderCartAdd(id)`
  (→ `cartDraft` → `POST /api/admin/carts`), an alert states plainly that it went
  to the builder, not the customer cart, and `admGo('admSecCart')` scrolls him to
  the builder section to finish (customer info + Generate cart link).
- **Worker** (`me.role === 'worker'`) — **hard no-op**, per the owner's rule
  *"los técnicos no tienen carrito — ellos solo ven los trabajos"*: no shopper
  mutation, no builder access, no customer pricing action. Only a short notice
  ("The cart is for customers only — technicians see jobs, not the cart."), and
  `orderNow` does not navigate to `#cart`.

Notices use `alert()` with hardcoded English, matching the admin builder's own
convention (`cartAddCustomLine` etc.); no menu re-render or label swap was
needed — the gate covers every Add/Order button because they all route through
`cartAdd`/`orderNow`.

# Builder hardening (2026-10-28, second pass)

The owner ordered the admin cart builder itself — *Admin → Cart*, the tool
that creates client payment links, "la máquina de hacer billete" — hardened
end-to-end with proof, and the legacy path above sealed. Method: the builder
was exercised the way Gabriel uses it on his phone, in a suite-style VM
fake-DOM harness driving the real `index.html` script, and over HTTP against
the real server booted the way `tests/run.mjs` boots it (mock Stripe for the
checkout pin). Baseline before this pass: **PASS 1188 / FAIL 0** (verified).

## Verified working (E2E evidence, no defect)
- **Picker**: search "starter" filters the 98-service catalog to the Starter
  Replacement row @ $225; other services disappear.
- **Adds**: `builderCartAdd` puts the starter in `cartDraft` at the $225
  catalog floor with its catalog name and paints the line editor into
  `#cartBuilderLines`; adding the same service again merges qty (no duplicate
  line); `cartSetQty` clamps/edits qty.
- **Prices + summary math**: a price edit inside the $225–$300 range ($275)
  renders list **$275.00** / member **$220.00**; adding a custom materials
  line ($60) and two Labor-$75 hours renders list **$485.00** / member
  **$400.00** — materials never discount, labor does, exactly the member-math
  exemption. (Server keeps the builder's prices by design — "your quote
  wins" — and recomputes totals from name/price/qty/kind alone.)
- **Generate**: POSTs the full draft + customer fields to
  `POST /api/admin/carts`; the link is painted for copying and the draft
  resets. Empty-draft Generate alerts and posts nothing.
- **Public link**: a $225 starter cart renders for a guest with the deposit
  law applied — **$50.00 deposit / $175.00 balance** (flat tier ≤ $300);
  guest checkout in mock Stripe charges only the $50 (session
  `amount_total` 5000). At $275 the deposit is still $50, balance $225.
- **Edit round trip**: Edit loads an open cart's lines back into the draft
  (banner up), Save PUTs to the same cart id — the link never changes — and
  the public page reflects the new totals. Cancel kills the link (page says
  cancelled; checkout is refused before any Stripe call). Non-admin create
  is 403.
- **SSE clobber probe — SAFE**: admin SSE events fire `loadAdmin()`, which
  re-renders `renderCartPicker()` + `loadAdminCarts()`, but nothing in that
  chain touches `cartDraft`, `#cartBuilderLines`, or the builder's customer
  inputs. Proven in the harness: a mid-quote draft, the typed customer
  name, and the line-editor DOM are byte-identical after a full
  `loadAdmin()` (the requests-section typing-guard problem does not exist
  here — the builder lives in static markup, not a re-rendered container).

## Defects found + fixed
1. **Blanked line name → silently short link (FIXED, client-side).**
   Every draft line's name is an editable input, including catalog lines.
   Reproduced end-to-end: blank the starter's name in the builder and the
   link still generates — but the server's item filter
   (`normalizeCartItems`, `server.js`) drops nameless lines **without any
   error**: a $225 starter + $125 door came back as a **$125 cart**; a
   blank-only cart 400s with a raw message. The customer would have been
   sent a link totaling less than the builder showed.
   Fix (`app/public/index.html` only): `builderNameProblem()` guard checked
   at the top of both submit paths (`createCartLink` + `saveCartEdit`) —
   any draft line with an empty name stops the submit with a plain alert
   ("Every line needs a name — it is what the customer sees on the link…").
   Same guard pattern `cartAddCustomLine` already used. `server.js`
   untouched (its filter behavior is now pinned as a documented fact).
2. **Legacy `#order` converter ignored roles (SEALED).** Reproduced: an
   admin or worker session opening an old `#order/<service>` link got the
   service written into the shopper cart and landed on `#cart`.
   Fix: `cartAddWithAddons()` now calls `cartRoleGate(id)` first and
   returns whether it added — admin → builder draft (base service; the
   link's add-ons don't carry into a draft line, and the gate's alert says
   where the service went), worker → hard no-op notice, guest/customer →
   byte-for-byte unchanged (add-ons, checkout prefill, toast, `#cart`).
   When the gate handles the conversion, `retireOrderRoute()` consumes
   the `#order` hash (`location.hash = ''`) so a later `render()` cannot
   re-fire it, and skips the prefill + `#cart` landing; through
   `render()`, a worker ends on his canonical `#worker` home.
3. **Stale builder copy (corrected, observed — not a functional defect).**
   The builder header told Gabriel the customer "pays in full" — wrong
   since the v79 deposit law and contradicted by the builder's own
   success message. Now: "pays the deposit to book — the balance is due
   at completion."

## Observations (not fixed — not reproduced as defects)
- The unfiltered picker shows the first 60 of 98 services; the rest are

- After a successful Generate, the customer name/phone/email/note fields
  keep their values (the draft clears). Harmless for back-to-back quotes
  to the same customer; left as-is.
